# M1.2 fixed v1: managed modeling identity and read-only consumer qualification

Status: DESIGN_FIXED_FOR_IMPLEMENTATION; not a runtime or user acceptance. M1.1 local preparation remains unchanged. This is a thin INIT facade over the existing durable OM identity ledger/native workflow, not a new native universal task engine. M1.3 resources and modeling write permission are not enabled.

## 1. Current chain and authority

Atlas `OmConfiguration` injects the actual `OmInstanceRegistry.client(instance, scope, actor)` into model source, direction, draft and projection clients. The current registry reloads a private static actor→token file. Existing P1 `OmIdentityJdbcLedger` + `JdbcOmIdentityTaskStore` + `OmIdentityNativeWorkflow` already persist account identity, original effect/UNKNOWN, managed UUID, credential reference/epoch and owned quarantine objects. They are reused.

M1.2 adds an exact scope mapping catalog `(tenant,space,project,account,instance)` referencing the global managed identity `(tenant,account,instance)`. Managed presence, including PENDING/DISABLED/UNKNOWN, seals the tuple: no fallback to a legacy token. A simultaneous legacy principal for that same tuple is CONFLICT, never a union. Unmanaged tuples retain existing legacy behavior. No per-person file edits or restarts establish a new binding.

Every management request resolves current Atlas subject and exact enabled project on the server. It requires current project ADMIN **and** current authority to manage the selected system user, including department/data scope. These checks run before historical-key lookup, native dispatch and result delivery. Target membership is freshly resolved. A USER sees/checks only their own mapping in an authorized project. Neither a body actor/scope/credential reference nor equal email/name establishes authority or identity ownership.

The existing global native identity may serve multiple projects. Scope DISABLE/REVOKE closes only the current tuple, leaving the native user and other projects untouched. ROTATE uses the existing global credential rotation, requires personnel management plus ADMIN for every current affected mapping, and previews all exact impacted scopes. It retains UUID and invalidates the old epoch/cache. This node does not offer global native soft-delete.

## 2. Public API (all under `/admin-api/ontology`)

Strict duplicate/unknown keys are rejected. IDs follow the locked M0 schema. No public object contains origin, filesystem path, credentialRef, password, token or raw native response.

- `GET /modeling-access/context?projectId`: `{contractVersion:1,projectId,scope,projectVersion,currentAccountId,canManage,instances:[{instanceId,name,available,reason}]}`. `reason` is always string, empty when available. The deployment-owned instance directory exposes labels/availability only. `canManage` is the current management intersection; per-candidate authorization is rechecked separately.
- `GET /modeling-access/candidates?projectId&q?&cursor?&pageSize?`: locked M0 MemberCandidates `{items:[{accountId,name,eligibleRoles,managedIdentityState}],nextCursor}`. Default20/max100; opaque cursor binds actor, tenant, exact project, filter and candidate cut. USER cannot enumerate candidates.
- `GET /modeling-access?projectId&accountId&instanceId`: locked M0 ModelingAccess, all12 fields. `qualifications` is all15 locked capabilities in contract order, each NOT_VERIFIED with null verifiedAt/evidenceRef. MAPPED requires exact managed UUID/positive bindingVersion/credentialEpoch. `version` is scope configuration version (unconfigured virtual view1; initial prepare expectedVersion null).
- `POST /modeling-access/prepare` + X-Request-Id: locked M0 ModelingPrepare, restricted to required six fields and `capabilities:["MODEL_READBACK"]`; rejects optional M1.3 targetId/createReservationName and every other capability. `change=CONFIGURE|REVOKE|ROTATE|DISABLE`. The capability is a readback category, never a grant or positive model-resource qualification.
- prepare returns locked M0 Plan (family INIT), immutable full body/hash, 15minute expiry. Server-owned operation is PROVISION_IDENTITY or CONFIGURE_MODELING_ACCESS, REVOKE_MODELING_ACCESS, ROTATE_IDENTITY or DISABLE_IDENTITY. Items identify managed identity and exact scope binding; rotation adds every shared affected scope. `changes`/`limitations` distinguish local binding effects, quarantine identity objects, pending consumer proof and zero modeling write authorization. Hash binds complete request/current identity/config/project cut and exact shared impact.
- `POST /modeling-access/confirm` + X-Request-Id: locked M0 ConfirmPlan `{planId,planHash,operationKey,cut}`. Loads server immutable plan, validates family/operation/hash and current authority/cut before any historical key. Returns locked M0 Intent only after durable transaction. Native work links the **existing** identity task; no network in the local transaction. Same key+same immutable plan returns original intent; changed content rejects. A confirmed existing native UUID is reused and only missing local binding is supplemented. UNKNOWN does not trigger another create/sync task or new key.
- `GET /modeling-access/intents/by-key?projectId&operationKey` and `GET /modeling-access/intents/{taskId}?projectId`: `{intent:<M0 Intent>,state:READY|RUNNING|SUCCEEDED|UNKNOWN|REQUIRES_OPERATOR,access:<M0 ModelingAccess>,taskState:string|null,allowedActions:[READ_ORIGINAL|PREPARE_NEW],reason:string}`. READY/RUNNING allow no new submit. UNKNOWN/REQUIRES_OPERATOR allow only READ_ORIGINAL, preserve original UUID/reservation/native task/effect evidence. PREPARE_NEW is offered only after SUCCEEDED and still requires a new current-version plan. Scope-only changes have their own persisted INIT receipt; they do not reuse M1.1 LOCAL_PREPARATION operation or manufacture native tasks.
- `POST /modeling-access/check` + X-Request-Id: locked M0 ModelingCheck exact six fields `{projectId,accountId,instanceId,expectedVersion,capabilities:["MODEL_READBACK"],mode:"READ_ONLY"}`. USER self allowed, manager target allowed only current intersection. Creates a persisted, expiring, single-use qualification inspection. No native objects, policies or source data are modified by this check; Basic session creation uses the mapped ordinary credential and is reported as authentication, not a model write.

Check response:

```
{inspectionId,projectId,accountId,instanceId,scope,configurationVersion,
 identity:{nativeUserId,bindingVersion,credentialEpoch},
 checks:[{consumer:"MODEL_CLIENT"|"WORKER",
   state:"NOT_VERIFIED"|"VERIFIED"|"DENIED"|"UNAVAILABLE"|"UNKNOWN",
   configurationVersion:positive|null,bindingVersion:positive|null,
   credentialEpoch:positive|null,nativeUserId:UUID|null,
   observedAt:ISO|null,evidenceRef:opaqueId|null,reason:string}],
 qualifications:<all15 NOT_VERIFIED>}
```

Exactly one check for MODEL_CLIENT and one for WORKER. Consumer failure does not erase a separate successful consumer fact. All returned successful cuts are current on delivery; changed account/scope/configuration/identity/epoch invalidates late response. ViewBasic/current-user success never enables semantic write, target readiness or MODEL_READBACK qualification.

## 3. Durable state and native management channel

New migration tables: scope mapping, immutable modeling plan, modeling intent, read-only inspection (bounded TTL), necessary audit; global identity/password/task/step receipts remain in existing om_identity tables and private credential store. No browser journal is authoritative.

CONFIGURE without global managed identity records one existing-ledger PROVISION intent after both permissions. Existing confirmed BOUND identity reuses UUID and epoch. Existing PENDING/UNKNOWN/conflict refuses a fresh native action and links/reads the original task. The native workflow creates its own quarantine Policy, Role, Team and ordinary non-admin/non-bot User. Empty grants mean no modeling write authority, **not zero policy objects**. It never adopts a same-name foreign user, even if email matches.

Platform-only approved instance origin/TLS/Basic provider/native build pin/management token reference/Secret Store root/runtime proof remain deployment configuration. Daily people/project mappings live in the catalog. The existing runtime registry's nonempty controlledTables requirement must not be satisfied with a fabricated table for a new project. Identity-only journal projection may use its existing Function<String,Instance> constructor with empty controlled sets, with coverage explicitly not observed; or reuse a genuinely configured platform identity instance without granting its source resources. No source grant/table existence is manufactured.

Native I/O remains outside local transactions, request deadline15s, immutable before-send receipts, existing claim/epoch fences and UNKNOWN handling. No blind native write retry or post-timeout new-account creation.

## 4. Real model/Worker consumers

The actual Java OmInstanceRegistry gets a managed resolver. The resolver reads current mapping/global binding each request, obtains an ordinary Basic session via the existing broker and guards current account/project/UUID/configuration/binding/epoch before dispatch and after response. It supplies the same OmRestClient consumed by existing model factories. Prior to M1.3 its authority allows only explicit read-only qualification (current-user and version); semantic write calls remain denied, including calls through projection/draft factories. Missing mapping is not a reader/admin fallback.

The real Worker `atlas-cloud/integrations/ontology-worker/src/atlas_ontology_worker/deployment.py` / `create_runtime_app` gains a dedicated `CHECK_MODELING_IDENTITY` operation and route. Old operations retain their static Principal scope restriction. The new operation accepts only an Atlas-persisted inspection ID/cut, not arbitrary actor/scope/credentialRef. A distinct trusted callback authenticates the Worker and resolves a current single exact-scope admission, with expiry/one-use CAS and all current identity versions. It cannot use `*` or a copied startup scope list to authorize a new project. The actual Worker OM client factory then reads the corresponding ordinary user's own UUID and rechecks the admission before returning. No business rows, source metadata capture or modeling writes occur. M6 source capture/provider-file replacement is explicitly not implemented here.

Machine credential transport detail is a Root technical decision before implementation: either a tightly bounded internal in-memory ordinary OM_USER session ticket (never public/persisted/logged) consumed by the actual OmClient, or an explicit restricted relay adapter in that same factory. No management credential/PAT is transferred. This pending detail does not alter the frozen public DTOs.

### 6.1 Fixed implementation choices after Root technical decision

- `normalizationVersion="atlas-modeling-access/1"`. Plan operation strings are exactly those listed in §2; identity create chooses PROVISION_IDENTITY, local reuse chooses CONFIGURE_MODELING_ACCESS. Configuration cut is scope mapping version (virtual1 before first mapping), identityVersion is actual positive global bindingVersion when present; credentialEpoch omitted when absent. Project version and all selected affected scopes are additionally bound inside the server plan hash. No placeholder identityVersion/epoch is invented.
- Unconfigured NOT_MAPPED prepare uses `expectedVersion:null`; any persisted scope row uses its displayed positive version, including disabled. Configure against a different existing global identity epoch preserves that existing UUID and prepares from its actual current cut.
- Plan items use IDENTITY and BINDING; rotation adds SCOPE items. PhysicalId is an opaque fixed `account:<numericAccount>:instance:<approvedId>` identity anchor or `project:<opaqueProjectId>` scope anchor; no filesystem path. All labels are in server changes text. Empty nativeId is null. No M1.3 target item is present.
- X-Request-Id is a separately validated request correlation ID; it need not equal operationKey. The durable confirm deduplication key is operationKey. Prepare X-Request-Id may be independent.
- Worker direct native consumption is selected. The distinct internal callback can temporarily borrow the mapped ordinary OM_USER access token, never password/refresh/management/PAT. Admission is a persisted inspection bound to exact actor/scope/instance/configVersion/bindingVersion/epoch, expires after120s and borrow CAS succeeds once. A per-inspection random internal proof (only digest persisted) binds subsequent current-before/current-after/finish callbacks; borrowed token never goes into public DTO, files, diagnostics, traces or browser.
- Borrow's short validity belongs to the inspection, **not a claim that the OM JWT itself has a short exp**. Worker uses the actual OmClient with a single native GET `/v1/users/loggedInUser`, verifies non-admin/non-bot/non-deleted and exact UUID/name/email, then releases references. Python strings are not claimed to be fully zeroed. Failed/lost borrow ACK cannot be replayed: inspection becomes UNKNOWN, a later separately created read-only check may be attempted; no account/rotation operation follows from this failure.
- `current` validates that exact borrowed inspection+internal proof and all current cuts, without returning another token. `finish` CAS commits only one safe UUID/version receipt after the same current checks. Replayed borrow/finish, expired admission and changed cuts are denied. Worker route receives only inspectionId; current scope/actor come exclusively from the callback. Old static Principal authorizes no new scope and never contributes authority to this operation.

### 6.2 Authority stamp clarification (supersedes the provisional §5 spelling)

The sole new native task authority is `MODELING:<intentUUID>` (45 ASCII characters). This is not a permission by itself. The native dispatch guard must load that exact durable modeling intent, require matching native task, original initiator and exact tuple, still-valid current configuration/project cut, current target account management permission and current ADMIN on every affected scope. New stamp handling preserves the original P1 authorities/rotation path. The narrowly extended ledger path is `atlas-module-infra/atlas-module-infra-api/src/main/java/cn/iocoder/atlas/module/infra/api/omidentity/OmIdentityJdbcLedger.java`; before bytes are captured before mutation. §4's pending transport paragraph is resolved solely by §6.1's explicit Root decision; no alternative relay is implemented.

### 6.3 Forward implementation clarifications

- Locked ModelingAccess contains11 required fields, not the oral12 count in §2; the exact11-field Java/public shape is unchanged. Resource Ids are max64; ConfirmPlan.operationKey and X-Request-Id independently follow the actual M0 pattern `[A-Za-z0-9_.:-]{1,128}`. An earlier Root suggestion that every key was64 was corrected against the machine schema/OpenAPI; no contract field was changed.
- Initial durable dispatch adds `OntologyModelingTaskDispatcher`, plus narrow `JdbcOmIdentityTaskStore.claimInitial` and `OmIdentityBackgroundExecutor.tickExactInitial`. It scans only new modeling-intent→original-native-task links with READY/attempt0/dispatched0, then performs the eligibility check inside the original locked claim transaction. Restart/commit-to-queue gaps recover that original task; no GET triggers dispatch, no new task is manufactured, and UNKNOWN/attempt>0 never enters this initial dispatcher. Existing global scan/recovery behavior remains separate.
- When modeling-access is enabled, the runtime executor factory resolves the modeling Store and installs its current gate before its existing start lifecycle. The actual legacy resolver is installed in Store configuration **before** guard registration/dispatcher startup, and an uninstalled legacy resolver fails closed. A changed legacy exact tuple is bound into the prepare fingerprint and rechecked before new confirm writes and native dispatch; consumer-only later CONFLICT would have been too late.
- Lost/failed Worker borrow and expired borrowed inspections preserve UNKNOWN; replay is denied. Worker finish phase and safe receipt share one local transaction; receipt failure rolls phase back and records UNKNOWN. A successfully FINISHED/VERIFIED original receipt is not erased by a later transport failure or expiry settlement. Global exception logging is bypassed only for the two new bounded controllers by a local fixed-error/no-store advice; proof-bearing request bodies never flow into its generic log branch.
